# Internationalization (i18n)

The system speaks **English (`en`, default/fallback)** and **Vietnamese (`vi`)** end to end. The
frontend renders localized UI; the backend localizes its API responses. Both are driven by the
**`Accept-Language`** header so the two stay in sync.

## Flow

```
User picks language (web LanguageSwitcher)
  → persisted in the `i18next` cookie + i18next.changeLanguage
  → axios sends `Accept-Language: <lng>` on every API call
  → backend RequestLocalization middleware sets the request culture
  → ILocalizationService resolves message keys → localized text in ApiResponse
```

## Backend (`api/`)

User-facing strings are **message keys**, never inline English. Keys are resolved centrally — handlers,
repositories, validators, and controllers only ever carry keys.

- **Keys live in** `api/src/ClassManagement.Infrastructure/Resources/en.json` and `vi.json`
  (flat `"Dotted.Key": "text"` maps, embedded in the assembly).
- **Resolution**: `ILocalizationService` (`Application/Interfaces/Localization`) →
  `JsonLocalizationService` (Infrastructure). Resolves against `CultureInfo.CurrentUICulture`,
  falls back to the default culture, then to the key itself if missing.
- **Where keys are turned into text**:
  - `BaseApiController` — localizes the `message` of every success response.
  - `GlobalExceptionHandler` — localizes the exception `message` **and** each validation error entry.
  - Rate-limiter rejection — localizes `Error.TooManyRequests`.
- **Culture detection**: `app.UseRequestLocalization(...)` (in `Api/DependencyInjection.cs`), registered
  before the exception handler so error responses are localized. Cultures come from the `Localization`
  config section (`DefaultCulture`, `SupportedCultures`) → `LocalizationOptions`.
- **Validators** (FluentValidation) use `.WithMessage("Validation.X.Y")` — the key, not English. The
  handler localizes each error.

### Adding a backend key

1. Add the same key to **both** `en.json` and `vi.json`.
2. Reference it where the string is produced (`throw new BadException("Auth.Foo")`,
   `.WithMessage("Validation.Foo")`, `return ApiOk(dto, "Auth.Bar")`).
3. Keep `en` text identical to any previous literal so existing tests that read `data` stay valid.

## Frontend (`web/`)

- **Translations live in** `web/public/locales/<lng>/<ns>.json`, one file per namespace
  (`common`, `auth`, `booking`, `dashboard`, `mentor`, `payment`, `public`).
- **Config**: `app/config/languages.ts` (supported languages, default, cookie key) and
  `app/lib/i18n.ts` (namespaces, fallback). SSR detection: `app/lib/i18n.server.ts`.
- **Usage**: `const { t } = useTranslation("<ns>")`. Switch with the `LanguageSwitcher`
  (`app/components/shared/language-switcher.tsx`), which updates i18next + the cookie.
- **SSR**: the server loads locale files via `i18next-fs-backend` and renders `<html lang>` to match;
  the client hydrates via `i18next-http-backend` with the detection order `cookie → htmlTag → navigator`
  (so there is no hydration mismatch).

### Adding a frontend key

Add it to the right namespace file under **both** `en/` and `vi/`. Use a new namespace only for a new
feature area (and register it in `app/lib/i18n.ts` `I18N_NAMESPACES`).

## Adding a new language

1. Backend: add the culture to `Localization:SupportedCultures` in `appsettings.json` and create
   `Resources/<culture>.json` (copy `en.json`, translate).
2. Frontend: add it to `SUPPORTED_LANGUAGES` in `app/config/languages.ts` and create
   `public/locales/<culture>/*.json` for every namespace.
